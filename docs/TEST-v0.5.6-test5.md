Unsigned local test build, November 17, 2026. No publication or signing yet.

## Trigger

The user's test 4 screenshot showed the direct reader's `Images exceed the single-file export memory limit` error. This confirms progress past the earlier unmapped-tool-images fallback, but the complete image-bearing conversation still had not exported successfully. Raising the old retained-string limit alone would not address the earlier OOM concern.

## Behavior

- Small exports retain their normal single-file behavior.
- Large saved-ChatGPT direct HTML/PDF exports split on message boundaries. Each file says Part N of M and gives its global message range, even when the title/date option is disabled. User reattachments and later repeated images remain in their proper messages.
- All parts are staged locally before any file is saved. HTML parts download sequentially, with numbered filenames, to Firefox's configured Downloads folder without a separate save prompt per part. Existing files are not overwritten. A failure after downloading starts reports incomplete output; files already saved may remain.
- PDF opens one print preview. Save the current part using Firefox, then select Next part; Previous part is available. Each part has a suggested numbered PDF filename. Only the current part's images are mounted in that page. Firefox's print dialog is still required for each PDF part.
- Intermediate parts use the extension's local IndexedDB, with one prepared part plus one message retained by the image builder. No conversation content or image bytes are uploaded. HTML staging is cleared after downloads; PDF staging is cleared when its preview tab closes. Failure/Stop triggers cleanup. Abandoned jobs expire after an hour of inactivity and are removed on a later storage access/background startup. See PRIVACY.md for the precise retention behavior.

## Image settings

Under Export options for HTML/PDF:

| Setting | Default | Effect |
| --- | --- | --- |
| Include user images | On | Keep images supplied in user messages |
| Include images from AI responses | On | Keep images in assistant responses and supported visible tool results |
| Show image source, size and quality details | Off | Add captions with source, stored dimensions, format and quality status |

Settings persist independently. Disabled categories are omitted before the direct reader downloads them or the page reader waits for/captures them. The website can still load its own images normally. TXT/Markdown/JSON behavior is unchanged by these HTML/PDF settings.

Direct PNG/JPEG/WebP/GIF bytes are embedded without resizing or re-encoding. The service may still supply a preview or previously compressed asset; equality with its original Download file has not been verified. Captions say so instead of claiming an original. Static SVG is sanitized. Page collection identifies PNG snapshots or linked images separately. Source labels identify the message author; an image in an AI response is not automatically asserted to have been generated by an image model.

## Limits

- Multipart applies only to the direct saved-ChatGPT HTML/PDF reader. JSON, Gemini, Selected, temporary chats, activity export and unsupported variants retain their existing page collection and limits.
- Parts target 12 Mi characters of prepared content, with room below the background's 16 Mi-character document limit. A single message up to 15 Mi characters can form a part by itself; larger single messages are rejected rather than split through arbitrary HTML/code structures.
- Existing per-image download (8 MiB) and pixel (16 Mi pixels) bounds remain. A part allows 24 Mi pixels across distinct image references and 128 image occurrences. A message that alone exceeds those bounds still stops preparation. The conversation-response and normalized-text limits remain.
- These bound extension data structures; they do not guarantee a maximum total Firefox/ChatGPT RAM footprint. Local disk quota can also stop staging. ZIP export with separate originals is not implemented.
